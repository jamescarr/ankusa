# Ankusa feature plan: content routing

## Context

Ankusa verifies, stores and delivers every hook of a source to every sink of that source. Nothing between the socket and the sink reads the body or the headers to decide *where* a hook goes: `Ankusa.Source` has no filter, no event type and no templated address (`packages/ankusa/lib/ankusa/source.ex:10-53`; `docs/configuration.md:203`: "every sink is tried on every delivered hook"). Every hosted webhook gateway (Hookdeck, Svix, Convoy) routes on event type, and every YAML user of Ankusa who wants one Kafka topic per event type, or one HTTP consumer per event family, has to run one source per family or write Elixir. This plan adds, in core and the YAML loader:

1. **`event_type:`** per source — the provider's event name, read from a header or a JSON path at ingest, stored on the hook, and carried to every consumer (CR-1, CR-4).
2. **`filter:`** per sink entry — a small data predicate over the event type, tenant, content type, headers and JSON paths; a sink whose filter does not match gets no delivery row (CR-2).
3. **`{{ var }}` templates** on the per-hook address keys of every sink (`topic`, `routing_key`, `subject`, `channel`, `message_group_id`, `ordering_key`, HTTP `url`/`headers`) for YAML and API-managed sources (CR-3).

CR-5 ties them into one worked example and one docs section. The ground rules of `ANKUSA_HARDENING_PLAN.md` (§Ground rules, 1–14) apply verbatim to every task here: the request path keeps rule 6 (one capped JSON decode shared by dedupe, ordering, event type and filters; no new process on the path), rule 3 (every new structure has a ceiling), rule 7 (new config keys are visible in `GET /v1/tenants/:t/sources/:name` and never secret-bearing), rule 9 (every format change is additive), rule 10 (bench gate on hot-path files) and rule 13 (every new key has a default, a range/shape check, a `configuration.md` row and a redaction decision).

- [ ] **CR-2 — Per-sink `filter:`: a data predicate decides which sinks get a delivery row** · P1 · Deps: CR-1 (after: 1)
  *Why:* a source's sinks all receive every hook (`docs/configuration.md:203`); the only way to send `invoice.*` to one topic and `customer.*` to another is one source per family, which splits the provider's single endpoint and its dedupe window. Rows are created per sink from `entry.sinks` in `Queue.prepare/3` (`packages/ankusa/lib/ankusa/queue.ex:118-134`), indexed by position in `Queue.Writer.build_ops/5` (`queue/writer.ex:1573-1577`), and archive replay already commits a subset of sinks by index (`writer.ex:551-561`): the row-creation seam exists, it only needs a predicate in front of it.
  *Change:*
  - **Grammar** (data; identical in Elixir, YAML and the admin API's JSON; map keys may be atoms or strings on the Elixir side):
    ```
    filter  := node
    node    := %{all: [node, …]} | %{any: [node, …]} | %{not: node} | %{field => matcher}
    field   := "event_type" | "tenant" | "content_type" | "header.<name>" | "json.<dot.path>"
    matcher := "literal" (equals) | ["a", "b"] (in) | %{op => value}, exactly one op
    op      := eq | neq | in | not_in | prefix | suffix | exists (boolean value)
    ```
    Ceilings (rule 3), each a config error when exceeded: ≤ 32 leaves per filter, nesting ≤ 4, a literal ≤ 256 bytes, `in`/`not_in` ≤ 64 values, header name ≤ 128 bytes, JSON path 1–16 non-empty segments; a map node has exactly one key; `all`/`any` lists are non-empty.
  - **Semantics.** Values: `event_type` → `env.event_type`; `tenant` → `env.tenant_id || "default"`; `content_type` → the media type of `env.content_type` (before the first `;`, trimmed, ASCII-downcased), `nil` when absent; `header.<name>` → the first value of that header (case-insensitive) from the complete request header list at ingest and the stored list at replay; `json.<path>` → `Dedupe.walk/2` on the shared decode: a binary → itself, an integer → its decimal string, a boolean → `"true"`/`"false"`, anything else → absent. Comparisons are byte-exact; `prefix`/`suffix` on bytes. On an absent value `eq`, `in`, `prefix`, `suffix` → `false`; `neq`, `not_in` → `true`; `exists: true` → `false`; `exists: false` → `true`. **Unevaluable** (a `json.*` leaf when the body is over `dedupe.max_json_bytes` or is not JSON): the whole filter answers `true` — a filter never loses a hook — and `[:ankusa, :dispatch, :filter_unevaluable]` `%{instance, source_id, tenant_id, sink: mod}` is emitted once per such sink. A sink without `filter:` is selected for every hook. No numeric comparison in this version (documented).

- [ ] **CR-3 — `{{ var }}` templates on per-hook sink addresses, for YAML and API-managed sources** · P1 · Deps: CR-1 (after: 1)
  *Why:* every messaging sink resolves its address per hook through `Ankusa.Sink.Messaging.resolve/2`, but only from an Elixir function (`packages/ankusa/lib/ankusa/sink/messaging.ex:93-108`); the loader builds static strings, so a YAML or API source cannot say `topic: events.<event type>` or `url: https://hooks.example.com/<tenant>` (`docs/delivery.md:334-350`).   *Change:*
  - New `Ankusa.Sink.Template` (`packages/ankusa/lib/ankusa/sink/template.ex`). Syntax: `{{ var }}` and `{{ var ?? fallback }}`, whitespace inside the braces optional; `var` ∈ `tenant | source | id | event_type | header.<name>`; `fallback` is a literal matching `[A-Za-z0-9._:/-]+`. A string on a templatable key that contains `{{` must parse entirely (an unknown variable, an unclosed `{{`, an empty `{{ }}`, a fallback with other characters, a `header.` with an empty name → config error); `}}` outside a template is literal; a literal `{{` cannot be expressed (documented). API: `template?(binary) :: boolean` (`:binary.match(s, "{{") != :nomatch`), `compile(binary) :: {:ok, t()} | {:error, reason}`, `compile!(label, binary)`, `render(t(), Envelope.t()) :: {:ok, binary} | {:error, {:template_missing, var}}`, `static(t()) :: nil`. Compiled form `{:template, [binary | {:var, name, fallback | nil}]}` (data, never a closure: the stored spec and `/v1/config` keep the string). Values: `tenant` → `env.tenant_id || "default"`, `source` → `env.source_id`, `id` → `env.id`, `event_type` → `env.event_type`, `header.<name>` → first value of the header from the stored list (so a `header.` variable on a header the `store_headers` policy drops is an error from `Template.check/2`, called beside `Ordering.check/2`). A missing value with no fallback is `{:error, {:template_missing, var}}`. Rendering never sanitises: an invalid broker name is the broker's error (permanent for Kafka `UnknownTopicOrPartition` as classified today).
